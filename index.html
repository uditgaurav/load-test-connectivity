Load testing · Connectivity

How load test traffic reaches the customer

Managed infrastructure generates the load. Traffic always leaves from our side. The customer only decides whether and how to let it in.

1. Default: public egress through NAT

The customer allows our static NAT IPs on their app port. They do not allowlist load pod IPs, and they do not allowlist their own IPs.

Request path
  1. User saves a script listing 5-6 endpoints and ports.
  2. Load Test Manager hands the run to K8s-IFS.
  3. K8s-IFS dispatches the DDCI manifest through NG Manager. The delegate applies it in the project namespace, and DDCR launches the load pods.
  4. Load pods send requests. NAT rewrites the source to our static public IP.
  5. Customer firewall sees that IP, matches the allow rule, forwards to the endpoint.
  6. Responses come back on the same connection. Metrics flow back to Load Test Manager.
  7. Run ends, traffic stops, final report goes to the user.
What the customer opens
  • Source: our NAT public IPs (all of them, if more than one).
  • Destination port: whatever each endpoint listens on (443, 8080, ...).
  • Not needed: load pod private IPs, our source ports (random, per connection), any inbound rule toward us.
  • Also ask for: WAF and rate-limit exemption, because all load comes from a few IPs.
What we must guarantee
  • Static, published egress IPs. Notice before any change.
  • Enough NAT IPs and ports (SNAT exhaustion causes timeouts under heavy load).
  • A test-identifying header (for example X-Load-Test: run-id) so the customer can filter.
  • Limit: this only works when the endpoints are reachable from the internet.

Is opening the destination port mandatory?

Not as a new step. The customer's app already listens on those ports. What matters is whether our traffic can already reach them.

Customer's current setupDoes the customer need to do anything?
Endpoint is public and open to the internet (for example :443 for real users)No. The port is already open. Nothing to change. Only consider a WAF or rate-limit exemption.
Endpoint is public but IP restricted (firewall, security group, ingress allowlist)Yes, one rule: add our NAT IPs to the allowlist for the ports the script uses.
Endpoint is private (internal IP only)Opening a port does not help. Use Private Service Connect or Tailscale (below).

So it is mandatory only when the app is IP restricted. The customer does not open a new port for us. They allow our source IPs on the ports the app already serves.

2. Private endpoints: Tailscale subnet router

For apps with private IPs, on-prem, or clouds other than AWS or GCP. The customer dials out, so they open no inbound port.

What the customer does
  • Runs a subnet router in their network.
  • Advertises the CIDR ranges that hold the endpoints.
  • Allows outbound only: UDP (Tailscale default 41641) for a direct path, or TCP 443 to a relay as fallback. No inbound port and no IP allowlist.
  • App ports (443, 8080, ...) stay private. They are reached inside the tunnel, so nothing is opened to the internet.
Trade-off
  • Good: easy to set up, quick to demo, works on-prem and on any cloud.
  • Bad: all load passes through the tailnet peer and subnet router. Past a point they become the bottleneck and add latency before the app reaches its limit.

3. Private endpoints: AWS PrivateLink / GCP Private Service Connect

The customer's cloud provider builds a private lane. Best for heavy load, but only when the app already runs on AWS or GCP.

What the customer does
  • Puts a load balancer in front of the endpoints.
  • Publishes it as an endpoint service and approves our connection request.
  • The port is whatever the load balancer listener exposes (for example TCP 443). One listener per app port.
  • No IP allowlist, and no CIDR overlap problem.
Trade-off
  • Good: handles heavy traffic far better than a tunnel.
  • Bad: only for apps already in AWS or GCP, and adds a per-GB cost.

Recommended approach (we run on Google Cloud)

Pick by where the customer's endpoints live. Start with the simplest option that works.

1. Cloud NAT with static IPs (default)

Use for public endpoints, including IP-restricted ones. Reserve static external IPs and attach them to Cloud NAT with manual IP allocation, so the egress list never changes. Add enough IPs and ports per VM for the peak connection count. Publish the IPs to customers.

Customer: allowlist our IPs on the ports the app already serves, only if the app is IP restricted.

2. Private Service Connect (private GCP customers)

Use when the customer's app is private and also on Google Cloud. Best for heavy load, with no public internet and no IP allowlist.

Customer: expose the app through an internal load balancer and a service attachment, then approve our PSC connection. PSC does not reach apps on AWS or on-prem.

3. Tailscale subnet router (everything else)

Use for on-prem, AWS, or other clouds with private endpoints. Quick to set up and cloud neutral. Treat it as the fallback because the tunnel limits throughput.

Customer: run a subnet router with outbound access only.

Skip Cloud Interconnect and Direct Connect. They need physical hardware and long lead times, so they are not worth it for load testing.
